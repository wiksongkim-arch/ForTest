# ForTest 源码公开与 GitHub 发布执行标准

> 版本：1.1
> 最近更新：2026-08-13
> 适用范围：ForTest 后续版本，以及同类 Windows 桌面项目的源码公开、GitHub 推送和回归发布。
> 核心目标：发布内容可用、可验证、无敏感信息，并且本地源码、远端提交和 CI 结果能够相互对应。

## 1. 术语和边界

- **开发仓库**：日常开发使用的仓库，可能包含历史提交、个人路径、本机配置和一次性材料。
- **公开快照仓库**：从允许公开的文件重新建立的干净 Git 仓库。它不继承开发仓库的 `.git` 历史。
- **发布候选提交**：已经通过本地测试、安装和启动验证，准备推送到 GitHub 的提交。
- **源码可见**：公众可以查看源代码，但权利仍由许可证限定。
- **开放源代码（Open Source）**：许可证应符合 OSI 对开源的定义。禁止商业使用的许可证通常不属于 OSI 开源许可证。

ForTest 当前使用 PolyForm Noncommercial 1.0.0，允许非商业用途查看、修改和分发，商业使用需另行取得书面许可。因此，对外应称为“源码公开”或“source-available”，不要误称为 OSI 开源。

## 2. 强制原则

以下规则适用于每次公开发布，不应因赶进度而省略：

1. 如果开发仓库历史中可能存在个人信息、业务资料或密钥，必须使用全新的公开快照仓库，不能直接公开原仓库。
2. `.gitignore` 只能阻止未来提交，不能清除已有 Git 历史；删除当前文件也不能消除历史泄露。
3. 公开内容采用**允许清单**复制：只复制已确认需要发布的目录和文件，不先全量复制再批量删除。
4. 源码、测试、安装包和 Git 历史分别做检查；任一检查不能代替其他检查。
5. 本地回归、打包、安装、启动均通过后，才生成发布候选提交。
6. 暂存、提交、推送是三个独立动作。使用自动化助手时，每个动作都必须获得明确授权。
7. 只暂存明确列出的路径，禁止使用 `git add .`、`git add -A` 或 `git add --all`。
8. 一个提交只解决一个可解释的问题；CI 修复按根因拆分，方便审查和回滚。
9. 推送后必须确认本地提交、远端分支和 GitHub Actions 对应同一 SHA。
10. 历史失败的 Actions 记录不会消失；验收以目标提交对应的最新运行结果为准。
11. `README.md` 与 `README.en.md` 必须作为中英文版本同步维护；修改任一版本时，在同一次提交中更新另一版本及对应语言截图。

## 3. 发布前输入

开始执行前，记录以下信息：

| 项目 | 必填内容 |
| --- | --- |
| 发布版本 | 例如 `0.2.13` |
| 开发仓库 | 本机绝对路径 |
| 公开快照仓库 | 独立的本机绝对路径 |
| GitHub 仓库 | 所有者和仓库名 |
| 目标分支 | 通常为 `main` |
| 许可证 | MIT、Apache-2.0、PolyForm Noncommercial 等 |
| 发布范围 | 源码、安装包、Release、文档中的哪些内容 |
| 已弃用功能 | 需要删除的目录、调用入口、构建项和文档 |
| 验收命令 | 单元测试、集成测试、打包、安装、启动命令 |

同时确认 GitHub 页面显示的账号与目标所有者一致。账号、仓库名或许可证有歧义时，暂停发布并先确认。

## 4. 目录分类标准

### 4.1 通常应公开

| 类型 | 示例 | 要求 |
| --- | --- | --- |
| 产品源码 | `windows_native/` 中的运行时代码 | 不含构建产物和本机配置 |
| 自动化测试 | `tests/`、模块内测试 | 不含真实账号、令牌和个人业务数据 |
| CI 配置 | `.github/workflows/` | 依赖版本应与正式构建一致 |
| 项目说明 | `README.md`、架构和安全文档 | 描述必须与实际功能和许可证一致 |
| 法律文件 | `LICENSE`、第三方声明 | 使用许可证官方原文 |
| 依赖清单 | requirements、锁文件、构建配置 | 能在干净环境复现 |

### 4.2 通常不应公开

| 类型 | 示例 |
| --- | --- |
| IDE 和助手状态 | `.idea/`、`.vscode/`、`.codex/`、`.codex-work/`、`.p/`、`.superpowers/` |
| 本机环境 | 虚拟环境、缓存、日志、覆盖率结果、测试临时目录 |
| 构建产物 | `build/`、`dist/`、安装目录、解压目录、隐私扫描中间结果 |
| 用户配置 | `data/settings.json`、数据库、凭据、会话和本机偏好 |
| 待删除内容 | `预删除/`、已废弃插件、旧交付包 |
| 一次性材料 | 日期化计划、验收报告、临时分析、开发助手草稿 |
| 密钥文件 | `.env*`、私钥、令牌、证书私钥、云服务配置 |

### 4.3 必须人工复核

- 文档、截图、录屏和错误日志；
- 示例配置、测试 fixture 和演示数据；
- Word、Excel、PDF、压缩包等二进制文件及其元数据；
- 含作者、公司、业务系统、钉钉/企业链接或本机路径的文件；
- 任何看起来“只是测试值”的密钥形式字符串；
- 第三方二进制、字体、图标和模板的再分发许可。

`docs/` 不是天然可删除目录。长期有效的架构、安全、开发和发布标准可以提交；一次性计划、扫描报告和验收记录应留在受忽略目录。

## 5. 标准执行流程

### 阶段 A：冻结范围并记录现状

1. 查看当前分支、工作区变更和远端：

   ```powershell
   git status --short
   git branch --show-current
   git remote -v
   git log -1 --format="%H %an <%ae> %s"
   ```

2. 不覆盖或清理用户已有的未提交变更。
3. 列出此次明确要删除、保留、公开和忽略的内容。
4. 检查 `.gitignore` 是否与目录分类一致。

### 阶段 B：完整移除已弃用功能

以移除插件为例，必须同时检查四个层面：

1. **文件层**：运行目录、插件包、资源文件是否已移出活跃源码树。
2. **调用层**：导入、命令路由、UI 入口、后台任务和配置项是否仍会调用。
3. **构建层**：打包脚本、依赖清单、安装器和 CI 是否仍包含该功能。
4. **文档与测试层**：README、帮助文本和测试是否仍将它描述成可用功能。

推荐搜索：

```powershell
rg -n -i "插件名|包名|旧命令名|旧配置键" .
rg --files | rg -i "插件名|旧目录名"
```

允许保留为数据迁移或向后兼容而存在的字符串，但必须能说明其用途，并证明它不会重新启用已弃用功能。

### 阶段 C：隐私与凭据审计

审计至少覆盖以下范围：

1. 当前将公开的文本文件；
2. 二进制模板、图片元数据、压缩包和安装包内容；
3. Git 作者姓名和邮箱；
4. 全部将公开的 Git 历史；
5. CI 配置、示例和测试数据。

重点搜索：

```powershell
rg -n -i --hidden `
  -g '!.git/**' `
  -g '!build/**' `
  -g '!dist/**' `
  "password|passwd|secret|token|api[_-]?key|private[_-]?key|authorization|bearer"

rg -n -i --hidden `
  -g '!.git/**' `
  "C:\\Users\\|D:\\|@qq\.com|@163\.com|@gmail\.com|钉钉|alidocs|公司名|真实姓名"

git log --all --format="%H`t%an`t%ae`t%s"
git rev-list --objects --all
```

审计判断：

- 命中不等于泄露，应逐项区分真实秘密、占位符、文档说明和测试构造值。
- 测试用假密钥尽量在运行时拼接，避免触发静态扫描，也避免使用外观接近真实凭据的固定字符串。
- 示例 IP 使用 RFC 5737 文档网段，例如 `192.0.2.1`、`198.51.100.1`。
- Git 提交作者优先使用 GitHub `noreply` 邮箱。
- 若旧历史存在风险，建立新仓库比重写公开前的复杂历史更稳妥。

发现真实密钥时，应先在服务端撤销或轮换，再删除文件和历史。仅删除文件不是补救措施。

### 阶段 D：确认许可证和对外表述

| 目标 | 常见选择 | 对外表述 |
| --- | --- | --- |
| 允许商业和非商业使用 | MIT、Apache-2.0 | 开源软件 |
| 公开源码但禁止商业使用 | PolyForm Noncommercial 等 | 源码公开 / source-available |
| 暂不授予复制修改权 | 保留所有权利 | 可查看不等于可复用 |

要求：

- `LICENSE` 使用许可证官方文本，不自行删改关键条款。
- `README` 明确许可范围、商业授权方式和第三方组件不自动受本项目许可覆盖。
- GitHub 显示 `Other` 或无法识别非标准许可证，不代表许可证无效；以仓库中的正式文本为准。
- 许可证变更通常只影响新授权，不能简单撤回已按旧许可证获得的权利，变更前应做法律评估。

### 阶段 E：建立干净公开快照

当开发历史不适合公开时：

1. 创建一个新的同级空目录。
2. 根据允许清单复制源码、测试、CI、长期文档和许可证。
3. 不复制 `.git/`、本机配置、构建产物、一次性材料和待删除目录。
4. 在新目录执行 `git init`，配置 GitHub `noreply` 作者信息。
5. 再做一次隐私扫描和文件清单复核。

示例骨架：

```powershell
$WorkRepo = 'D:\path\Project-dev'
$PublicRepo = 'D:\path\Project-public'

New-Item -ItemType Directory -Path $PublicRepo
Copy-Item -LiteralPath "$WorkRepo\README.md" -Destination $PublicRepo
Copy-Item -LiteralPath "$WorkRepo\LICENSE" -Destination $PublicRepo
Copy-Item -LiteralPath "$WorkRepo\src" -Destination $PublicRepo -Recurse
Copy-Item -LiteralPath "$WorkRepo\tests" -Destination $PublicRepo -Recurse
Copy-Item -LiteralPath "$WorkRepo\.github" -Destination $PublicRepo -Recurse

git -C $PublicRepo init -b main
git -C $PublicRepo config user.name 'GitHub账号'
git -C $PublicRepo config user.email 'GitHub-noreply邮箱'
git -C $PublicRepo status --short
```

不要复用已有非空公开目录，也不要用递归删除命令“清空后重建”。新建目录更容易审计和回滚。

### 阶段 F：本地回归、打包和安装验收

按风险从低到高执行：

1. 静态检查和目标模块测试；
2. 全量自动化测试；
3. 正式打包命令；
4. 安装包内容隐私扫描；
5. 静默安装或标准安装；
6. 从安装目录启动应用；
7. 验证进程存活、主窗口出现且可响应；
8. 对核心业务路径做人工冒烟；
9. 记录安装包大小和 SHA-256。

计算安装包摘要：

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath 'D:\path\Product-Setup.exe'
```

最低业务冒烟应包含：启动、打开/新建主要对象、核心处理、保存或导出、异常提示、退出后再次启动。仅看到进程存在不能代表业务功能正常。

### 阶段 G：建立 GitHub 上传通路

优先顺序：

1. 已授权且具备写权限的 GitHub 集成；
2. GitHub CLI 或 HTTPS 凭据；
3. 仓库专用 SSH 部署密钥。

部署密钥规范：

- 每个仓库单独生成，不能跨仓库复用。
- GitHub 只保存公钥，私钥只留在可信本机。
- 仅在需要推送时启用写权限。
- 远端域名和 SSH 主机指纹必须验证。
- 网络限制 22 端口时，可使用 GitHub 官方 SSH 443 端口入口。
- 不在日志、截图、聊天或仓库中打印私钥。
- 设备遗失、人员变化或怀疑泄露时，立即删除 GitHub 部署密钥并换新。

使用 443 端口的远端示例：

```powershell
git remote add origin 'ssh://git@ssh.github.com:443/OWNER/REPOSITORY.git'
git remote -v
```

如需为单仓库指定密钥，应使用仓库级 `core.sshCommand`，并将密钥和已验证的 `known_hosts` 放在仓库外。不要把私钥路径写进可公开配置文件。

### 阶段 H：分批暂存、提交和推送

每次提交执行相同闭环：

```powershell
git status --short
git diff -- path/to/file1 path/to/file2
git add -- path/to/file1 path/to/file2
git diff --cached --check
git diff --cached --stat
git diff --cached
git commit -m "清晰描述唯一目的"
git status --short
git push origin main
```

规则：

- 路径必须显式列出；提交前同时查看未暂存和已暂存差异。
- `git diff --cached --check` 必须通过。
- CI 修复只提交实际相关文件，不夹带格式化或本机文件。
- 提交信息写“解决了什么”，不要写模糊的 `update` 或 `fix`。
- 推送成功后记录完整 SHA。

远端一致性校验：

```powershell
$LocalSha = git rev-parse HEAD
$RemoteSha = git ls-remote origin refs/heads/main | ForEach-Object { ($_ -split "`t")[0] }
$LocalSha
$RemoteSha
if ($LocalSha -ne $RemoteSha) { throw '本地与远端 main 不一致' }
```

### 阶段 I：监控和诊断 GitHub Actions

1. 确认运行关联的是目标 SHA，而不只是分支名相同。
2. 逐步查看失败 job 和 step，找到第一处真实错误。
3. 警告和根因分开处理；例如运行时弃用警告可能需要后续维护，但不一定造成当前失败。
4. 先在本地构造相同环境复现，再提交最小修复。
5. 修复后运行受影响测试和全量回归，再推送。
6. 最终记录绿色运行 URL、SHA、测试数、跳过数和已确认无害的警告。

### 阶段 J：创建并验收 GitHub Release

GitHub Release 不是“把本地安装包上传一次”这么简单。正式发布应形成以下可追溯链路：

```text
版本文件 → 发布候选提交 → Git 标签 → 云端构建 → Release 资产
        → 下载后摘要校验 → 安装 → 启动与业务冒烟
```

#### J.1 发布顺序

1. 先把可复用的 Release 工作流提交到默认分支，并确认普通 CI 绿色。
2. 在发布候选提交中统一应用版本号，确认安装器、程序属性和发布文件名使用同一版本。
3. 对发布候选提交创建**附注标签（annotated tag）**，不要只依赖可移动的分支名。
4. 推送标签后，校验标签最终指向的提交，而不只比较标签对象本身。
5. 从默认分支手动触发 Release 工作流，把已有标签作为输入；工作流必须检出该标签对应的源码。
6. 云端重新执行完整构建、测试、隐私门禁、安装包生成和摘要计算。
7. 发布安装包及独立的 `.sha256` 文件，再从 GitHub Release 下载资产进行最终验收。

推荐校验命令：

```powershell
$Version = '0.2.13'
$Tag = "v$Version"

# 附注标签本身有独立对象 SHA，验收时要取标签最终指向的提交。
$TagCommit = git rev-parse "$Tag^{}"
$RemoteTagCommit = git ls-remote origin "refs/tags/$Tag^{}" |
    ForEach-Object { ($_ -split "`t")[0] }

if (-not $RemoteTagCommit) {
    # 轻量标签没有 ^{} 记录时，回退到标签引用本身。
    $RemoteTagCommit = git ls-remote origin "refs/tags/$Tag" |
        ForEach-Object { ($_ -split "`t")[0] }
}

if ($TagCommit -ne $RemoteTagCommit) {
    throw '本地与远端标签指向的提交不一致'
}
```

最佳实践是先让 Release 工作流存在于默认分支，再创建发布标签。虽然 GitHub 可以使用默认分支上的工作流定义去检出更早的标签，但这种先后关系不直观，容易让维护者误判标签内是否包含发布能力。

#### J.2 Release 工作流设计

- 默认采用 `workflow_dispatch` 手动触发，避免普通源码推送意外创建正式 Release。
- 输入必须是已存在的标签；工作流校验标签格式、版本文件、安装包版本和目标提交的一致性。
- `actions/checkout` 使用 `persist-credentials: false`，避免凭据继续留在 Git 配置中。
- 工作流默认权限保持只读，只对实际执行发布的 job 授予最小的 `contents: write`。
- GitHub 短期令牌只提供给创建、上传和发布后核验步骤，不传入测试、打包或第三方安装脚本。
- 固定第三方 Action 的稳定版本；高风险或供应链敏感场景可进一步固定到完整提交 SHA。
- 同一标签已经存在 Release 时默认停止，不静默覆盖资产、不自动删除 Release，也不移动已公开标签。确需替换时必须单独审批并保留原因。
- Release 创建失败时，先确认是否已生成草稿或部分资产，避免重试后出现同名重复文件或不完整发布。

#### J.3 Windows 构建工具链锁定

本次 ForTest v0.2.12 发布发现，系统包管理器提供的 Inno Setup 6.7.1 无法识别项目使用的 Inno Setup 7 `SetupArchitecture=x64` 指令。以后不能只写“安装最新版”或假设包管理器版本满足构建脚本，而应执行以下规则：

1. 根据安装器脚本实际使用的语法确定最低工具版本。
2. 固定经过验证的准确版本，并从项目官方发布地址下载。
3. 下载后同时校验 SHA-256 和 Authenticode 签名发布者，再执行安装或解压。
4. 在日志中输出工具版本，但不输出令牌、私钥路径或带凭据的下载地址。
5. 本地和 CI 使用同一主版本与构建参数；升级工具链时单独回归安装和卸载流程。

ForTest 当前验证基线为 Inno Setup 7.0.2，其官方安装程序 SHA-256 为：

```text
5AD54CA3DEF786F8F4212552E54CC6D8D61329E2D24A1CFEE0571D42C2684FF1
```

签名发布者应为 `Pyrsys B.V.`。该值只代表本次验证基线；升级版本时必须从官方发布页重新取得并独立核验，不能沿用旧摘要。

参考官方发布页：<https://github.com/jrsoftware/issrc/releases/tag/is-7_0_2>

#### J.4 Hosted Runner 环境与隐私门禁

GitHub Hosted Runner 会预置用户名、主目录和部分服务变量；这些值可能被严格隐私门禁误判为项目泄露。处理原则是隔离环境，而不是降低扫描强度：

- 为构建步骤创建位于 Runner 临时目录下的独立 `USERPROFILE`、缓存目录和应用数据目录。
- 只在具体构建步骤中清空与产品无关的继承变量，不修改 Runner 全局状态。
- 源码扫描只扫描公开快照，产物扫描只扫描最终打包目录和安装包；不要把整个 Runner 环境变量表写入日志或扫描报告。
- 不把真实 `GITHUB_TOKEN` 传给构建进程；发布步骤结束后也不继续复用。
- 若门禁命中 Runner 默认值，应记录命中来源并增加精确的环境隔离，禁止直接添加宽泛忽略规则。

#### J.5 Release 资产与说明

Windows 正式 Release 至少包含：

- 命名稳定且带版本的安装包，例如 `ForTest-Windows-x64-Setup-0.2.13.exe`；
- 对应的纯文本 SHA-256 文件，例如 `ForTest-Windows-x64-Setup-0.2.13.exe.sha256`；
- Release 说明，包括版本、支持平台、主要变化、许可证边界、安装包摘要、已知限制和代码签名状态。

README 截图和其他展示资产也属于发布内容，必须逐张以原始分辨率复核可见文本并清除元数据。即使文件已标记为“打码版”，仍需重新检查；优先生成名称明确的公开副本（例如 `2-public.png`），只把公开副本加入允许清单，不覆盖用于内部留档的原图。推送后还要打开 GitHub README，确认图片路径、大小写和渲染结果正确。

安装包如果没有 Authenticode 代码签名，必须在 README 和 Release 说明中明确提示可能出现 Windows SmartScreen 警告，不能用“安全软件误报”替代事实说明。

不同机器或不同时间构建的安装包未必能得到相同二进制摘要。正式对外发布后，应把 **GitHub 上实际下载到的资产**作为权威对象：云端构建先生成摘要文件，上传后再下载并重新计算；不得拿另一台机器上的同名安装包摘要代替线上资产摘要。

#### J.6 下载后最终验收

Release 页面显示“发布成功”不等于交付完成。必须从公开下载地址重新取得安装包和摘要文件，并独立验证：

1. Release 不是草稿，也没有被误设为预发布；版本标题和标签正确。
2. 资产名称、数量、字节数和 GitHub 返回的 digest 符合预期。
3. 下载文件的 SHA-256 与 `.sha256` 文件及 GitHub digest 三者一致。
4. PE 架构正确，程序文件版本与 Release 版本一致。
5. Authenticode 状态符合发布说明；未签名不能被记录成签名通过。
6. 对下载后的最终二进制再次执行用户名、本机路径、业务链接、API Key、JWT 和私钥标记扫描。
7. 检查公开 README 的链接和图片均能从 GitHub 正常访问与渲染。
8. 在干净或隔离目录执行安装，确认安装程序退出码为零。
9. 从实际安装目录启动，完成基础启动、完整后端加载、主窗口响应和核心页面人工冒烟。
10. 退出应用并确认没有异常残留进程；需要时再验证卸载。

涉及真实 Jenkins 部署、付费模型调用、线上数据写入等外部副作用的路径，除非发布授权明确要求，不应为了冒烟而直接触发。应记录未实调原因，并用自动化回归、连接检测和只读 UI 验证覆盖可验证部分。

## 6. Windows CI 常见故障基线

| 现象 | 常见根因 | 标准处理 |
| --- | --- | --- |
| Checkout 或 pip 安装时报 `Filename too long` | Windows 默认未启用长路径 Git 支持 | 在 checkout/安装前执行 `git config --global core.longpaths true` |
| 本地通过，CI 出现 CLI 行为差异 | CI 解析到的依赖版本与正式打包版本不同 | 在 CI 显式安装与构建一致的锁定版本，并打印版本验证 |
| 时间字符串相差数小时或跨日 | Runner 使用 UTC，代码隐式转换成本地时区 | 明确业务语义；保留输入时区的 wall-clock，或统一使用指定时区 |
| 路径断言失败，出现 `RUNNER~1` | Windows 8.3 短路径与解析后的长路径不同 | 比较前对双方执行 `Path.resolve()`，避免比较未经规范化的字符串 |
| 文件删除/替换偶发失败 | 进程、杀毒软件或测试仍占用文件 | 关闭句柄，使用有上限的重试，并记录最终占用信息 |
| 测试为 skipped 但 job 绿色 | 依赖或平台条件未满足 | 核实跳过原因；关键路径不允许仅靠 skipped 通过验收 |

时间和路径问题应通过代码语义和确定性测试解决，不要只把 CI Runner 时区或临时目录改成“恰好能过”的值。

## 7. GitHub Release 常见故障与处理

| 现象 | 根因或风险 | 标准处理 |
| --- | --- | --- |
| CI 安装的打包器不识别安装脚本指令 | 包管理器版本低于项目语法要求 | 固定官方已验证版本，校验下载摘要和发布者签名 |
| 标签 SHA 与预期提交看似不一致 | 附注标签有标签对象 SHA 和目标提交 SHA 两层 | 使用 `git rev-parse "TAG^{}"` 比较最终提交 |
| 工作流存在于 `main`，但标签内看不到该文件 | 工作流定义来自触发分支，构建源码来自检出的标签 | 最佳做法是先合入工作流再打标签，并在日志明确两者 SHA |
| 本地安装包和云端同名安装包摘要不同 | 构建环境、时间戳或打包器行为导致字节不可复现 | 以上传后的 GitHub 资产为权威对象，下载后重新校验 |
| 隐私门禁命中 Runner 用户名或服务变量 | Hosted Runner 的预置环境进入扫描范围 | 使用隔离用户目录并精确限制扫描范围，不降低门禁规则 |
| Release 已存在导致上传冲突 | 重跑工作流尝试覆盖同一标签或同名资产 | 默认停止并人工检查，未经审批不删除或覆盖正式资产 |
| Release 页面有资产但用户无法安装 | 只验证了上传，没有验证公开下载链路 | 从 Release 下载、验摘要、实际安装并从安装目录启动 |
| 安装包触发 SmartScreen | 未进行 Authenticode 代码签名 | 明确披露签名状态；正式商用前配置可信代码签名证书 |

## 8. 验收完成条件（Definition of Done）

以下项目全部满足，才可宣布本次源码发布完成：

- [ ] 已弃用功能的文件、调用、构建项和用户入口均已移除。
- [ ] 公开文件清单符合允许范围，没有待删除目录和本机材料。
- [ ] 当前源码、二进制文件和公开 Git 历史已完成隐私审计。
- [ ] 没有真实密钥、个人邮箱、本机绝对路径或私有业务链接。
- [ ] README、LICENSE 和实际许可范围一致。
- [ ] `README.md` 与 `README.en.md` 的章节、版本、链接、能力边界及对应语言截图保持一致。
- [ ] 目标测试、本地全量测试和共享测试通过；跳过项已解释。
- [ ] 正式安装包构建成功，隐私门禁通过。
- [ ] 安装成功，安装目录中的程序能够启动并响应。
- [ ] 核心业务流程人工冒烟通过。
- [ ] 安装包文件名、版本、大小和 SHA-256 已记录。
- [ ] 暂存内容只包含本次授权文件，`git diff --cached --check` 通过。
- [ ] Git 提交作者使用预期账号和邮箱。
- [ ] 本地 HEAD 与 GitHub 目标分支 SHA 完全一致。
- [ ] GitHub Actions 对该 SHA 的必要 job 全部绿色。
- [ ] Actions 的警告和 skipped 测试已审阅并记录。
- [ ] 公开快照工作区干净，或剩余变更都有明确归属。
- [ ] 部署密钥的所有者、用途和撤销方式已记录。
- [ ] 若发布 GitHub Release，标签、版本文件、发布提交和安装包版本完全对应。
- [ ] Release 工作流使用固定且已验证的构建工具链，并遵循最小权限原则。
- [ ] Release 资产至少包含安装包和独立 SHA-256 文件，说明中披露许可证及签名状态。
- [ ] README 截图已逐张复核、清除元数据并从 GitHub 页面验证渲染。
- [ ] Release 不是意外的草稿或预发布，资产名称、数量和大小符合预期。
- [ ] 从 GitHub 下载后的安装包摘要与摘要文件、GitHub digest 三者一致。
- [ ] 下载后的正式资产已通过二进制隐私扫描、安装、启动和 UI 冒烟。

## 10. 回滚与事故处理

### 普通代码缺陷

- 不重写已经公开且被他人获取的历史。
- 优先追加修复提交；确需回滚时使用 `git revert <sha>`，经测试后再推送。
- 修复提交仍需完成受影响测试和 CI 验收。

### 敏感信息已推送

1. 立即撤销或轮换密钥、令牌和密码。
2. 判断 GitHub fork、缓存、Actions 日志和 Release 是否也含副本。
3. 停止继续发布，并保存影响范围记录。
4. 使用适合的历史清理工具重写历史，随后强制更新远端；这是高风险操作，必须单独审批。
5. 通知可能受影响的维护者和服务所有者。
6. 清理后再次扫描，但仍把旧秘密视为已经泄露。

### 部署密钥异常

- 先在 GitHub 仓库设置中删除该公钥。
- 删除可信设备上的对应私钥副本。
- 重新生成仓库专用密钥，禁止复用旧密钥。
- 检查异常时间段内的提交、分支和 Actions 运行。

## 11. 禁止事项

- 不把开发仓库整体设为公开后再检查。
- 不把 `.gitignore` 当成历史清理工具。
- 不把构建通过等同于安装、启动和业务验收通过。
- 不为“让测试变绿”而降低关键断言、永久跳过关键用例或吞掉异常。
- 不把 CI 的所有红色都归因于 Runner 波动；必须找到首个实际失败原因。
- 不把个人访问令牌、SSH 私钥或真实 `.env` 放入仓库。
- 不通过聊天或日志传输私钥正文。
- 不在未经确认的账号或仓库上推送。
- 不将禁止商业使用的项目宣传为 OSI 开源。
- 不在没有单独授权时执行暂存、提交、推送、创建 Release 或改写历史。
- 不移动已经公开的版本标签来替换发布内容。
- 不静默覆盖或删除已发布的 Release 资产。
- 不使用未经版本、摘要和签名校验的第三方构建工具生成正式安装包。
- 不把本地同名安装包当作线上 Release 资产的验收替身。
